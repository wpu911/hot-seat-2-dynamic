# Flash Next R2 Stage 15：R9700 / RDNA4 head-dim-256 FlashAttention MMA

日期：2026-09-19

## 1. 为什么加这一阶段

R2 的长上下文工作此前主要盯着 QSA / TOP_K / pooled-key cache，这些更偏 TG 和稀疏索引路径。R9700 还有另一块很直接的 PP 空间：RDNA4 的 head-dim-256 FlashAttention。

上游 `ggml-org/llama.cpp#26419` 当前仍是 open PR，目标就是让 AMD RDNA 在 head dim 256 时进入 MMA FlashAttention，并在 DKQ > 128 时让 K/V 绕过 LDS staging。PR 作者在一张 Radeon AI PRO R9700（gfx1201，ROCm 7.2.4）上验证的 Qwen3.6-35B-A3B 数据里，TG 基本不变，而深上下文 PP 从 16K 开始有明显增长，64K/126K 的外部测试约为 +19%/+22%。这些数字只作为“值得测”的依据，不当作 Flash Next 在本机必然能拿到的收益。

另外，Luce/lucebox 的 `#736` 在 R9700 上对 Qwen3.8-27B 做了独立的 RDNA4 head-256 tensor-core FA 实现，外部测试同样显示收益随上下文加深而增大。两条实现并不相同，因此 R2 优先选择改动更小、仍在 llama.cpp 主线上审查的 `#26419` 做隔离实验。

## 2. 为什么不是简单做两套 binary A/B

`#26419` 同时改了两件事：

1. DKQ > 128 的 AMD WMMA kernel 本身；
2. RDNA4 head-256 的 dispatch 条件。

如果只做“原 binary vs PR binary”，即使变快也无法知道是哪个变化造成的；如果变慢，也不知道是不是 gfx1100 的既有 WMMA 路径被 kernel 改动拖累。

因此 Stage 15 是三臂：

```text
BASE
  原长上下文 winner，不含 #26419

PATCHED_OFF
  含 #26419 全部 kernel 改动
  GGML_RDNA4_FA256_MMA=0
  禁止新的 RDNA4 DKQ256 route

PATCHED_ON
  与 PATCHED_OFF 完全相同的 staged ELF
  GGML_RDNA4_FA256_MMA=1
  打开新的 RDNA4 DKQ256 route
```

这样：

```text
BASE -> PATCHED_OFF
```

专门检查 PR 的 kernel carryover 有没有伤到现有混合 GPU 路径；

```text
PATCHED_OFF -> PATCHED_ON
```

才是新的 R9700 dispatch 的净效果。

这比拿两个不同 binary 然后宣布“变量只有一个”稍微诚实一点。计算机已经够擅长制造幻觉式 benchmark，人类没必要帮忙。

## 3. 对 7900 XTX 的处理

PR 的新 route 受：

```cpp
GGML_CUDA_CC_IS_RDNA4(cc)
```

保护，因此 `gfx1100` 的 7900 XTX 不会进入新增的 RDNA4 dispatch。

但 PR 的 WMMA kernel 文件本身也有 DKQ > 128 修改，所以不能简单说“7900 完全没变”。这就是 BASE -> PATCHED_OFF 这一关存在的原因。

构建仍然同时编译：

```text
gfx1100
gfx1201
```

并要求 staged runtime 的 `--list-devices` 同时看到两张卡。

## 4. 准备

Phase-2 会自动把已经确认的长上下文 base 传进去：

```text
Modern MTP
   或
ROCm TOP_K winner
```

独立执行时：

```bash
bash flashnext-r2/scripts/prepare_stage15_rdna4_fa256.sh
```

如果要从已确认的 TOP_K winner 叠加：

```bash
BASE_SRC=/app/share/llama_box/src/llama.cpp-flashnext-r2-rocm-topk-20260918 \
BASE_ALIAS=qwen3.8-flash-next-r2-rocm-topk:256k \
bash flashnext-r2/scripts/prepare_stage15_rdna4_fa256.sh
```

prepare 会：

```text
固定 PR #26419 head
核对 PR 仍是 3 个文件
3-way apply
增加 process-local route kill switch
构建 gfx1100 + gfx1201
跑 FLASH_ATTN_EXT backend correctness
用 stage_runtime_bundle.sh 做私有 runtime / RUNPATH / SHA / ldd 验证
注册 OFF / ON llama-swap aliases
```

不会覆盖：

```text
qwen3.8-flash-next:256k
```

## 5. 测试

```bash
bash flashnext-r2/scripts/run_stage15_rdna4_fa256_ab.sh
```

走真实：

```text
llama-swap :8090
```

默认上下文：

```text
16K
64K
128K
```

三臂按：

```text
BASE OFF ON ON OFF BASE
```

执行。每个 arm 都先 cold unload，再 warmup，然后固定长度 TG + retrieval marker + MTP counter。

## 6. 通过条件

分析脚本：

```bash
python3 flashnext-r2/scripts/analyze_stage15_rdna4_fa256.py <result.json>
```

默认要求：

```text
BASE -> OFF:
  patched carryover 不得出现明显 PP/TG/MTP 回退

OFF -> ON:
  >=32K 深上下文 median PP 至少 +3%
  任一测点 PP 不得明显回退
  TG 最差不低于 -2%
  MTP acceptance 最差不低于 -3 percentage points

BASE -> ON:
  深上下文 median PP 至少净增 +2%
```

所有 arm 还必须：

```text
retrieval marker 正确
固定 TG 完整生成
MTP drafted / accepted counter 完整
```

不满足就留在原 base，不因为“看起来快了一点”进入组合阶段。

## 7. Phase-2 集成

新的顺序：

```text
Modern MTP
  -> ROCm TOP_K decision
  -> Stage15 RDNA4 FA256
  -> QSA gather
  -> pooled-key cache
```

只有 Stage15 PASS 时，`LONG_BASE_SRC/LONG_BASE_ALIAS` 才改成 FA256 ON；否则 QSA 继续从进入 Stage15 之前的 base 构建。

Phase-3 会从 `LONG_WINNER_SRC/LONG_WINNER_ALIAS` clone，因此 Stage15 如果胜出会自然进入最终组合，`GGML_RDNA4_FA256_MMA=1` 也会从 winner alias 继承，不需要再手工拼配置。

## 8. runtime 隔离

Stage15、Stage14 TOP_K、Modern Foundation、Modern MTP、Stage7 QSA、Stage8 pooled、Phase3 final 现在都走统一的：

```text
stage_runtime_bundle.sh
  -> normalize_runtime_rpath.sh
  -> verify_runtime_bundle.sh
  -> SHA256SUMS / symlink topology / version manifest
```

目标是保证删掉临时 `build-r2-*` 目录后 candidate 仍然能启动。之前那种 `cp build/bin/*` 然后祈祷 RUNPATH 没偷偷指回 build tree 的方式，已经从这些主路径清掉。
