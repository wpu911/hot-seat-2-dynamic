24G显卡，读上下文终于不拖后腿了

最近给本地 Ornith 做了一轮升级，终于把一个很别扭的问题掰过来了：明明开始回答以后速度还行，为什么每次发完消息，都要先等模型“读题”读半天？

这次最值得分享的，就是怎么让 PP 和 TG 配合起来。

先把两个词翻译成人话。

PP 是处理输入、建立上下文状态的阶段。你贴一大段材料、工具返回一长串结果，或者需要重新处理历史消息，主要就看它。

TG 是接着往外生成 token 的阶段，也就是模型开始回答以后，内容往外冒的速度。

只看 TG，很容易产生一种错觉：这模型不是挺快吗？真用起来才发现，回答前的等待才是大头。

我的环境是 Ryzen 9 9950X、192GB 内存、RX 7900 XTX 24GB，跑 Ornith-1.5-35B-A3B Q8_0。35B 的 Q8 权重不能全放进这张卡里，因此原本就有一套 CPU/GPU 协作、专家缓存和动态 KV 的机制。

之前主要照顾的是 TG。

生成时，一次处理的 token 很少，把经常用到的专家留在显存里，就能少搬权重。选中的专家如果没驻留，就由 CPU 路径补上计算。显存里既有固定保留的专家，也有能按空间调整的弹性部分。

这对连续生成很有用，但长输入来了以后，需求变了。

大批量 PP 更需要 GPU 的批量矩阵计算和工作空间。如果仍然让显存维持“尽量多塞解码专家”的布局，PP 就得挤着干活。更关键的是，原来的算子分配规则还可能把内存里的专家权重留在 CPU 上计算。

于是就出现了一个尴尬场面：显存已经腾出来了，真正该去 GPU 批量计算的活，却没跟着过去。

所以这次升级，核心是让同一块显存按阶段换工作。

长输入到来时，暂时退掉可以回收的那部分专家缓存，给 PP 腾出空间。固定基础部分仍然保留，KV 也不是随手清空重来。

接着，让符合条件的 Q8 专家批量算子进入 GPU。权重主体仍在系统内存，计算前把当前需要的专家权重张量搬进一个可复用的 GPU 暂存区，再交给现有矩阵内核处理。

在这个模型上，这块暂存区是 272MiB。它是一块权重张量的工作区，不是把整个模型搬进显存，也不是每个专家都额外申请一份。

这一步解决了“腾了空间，却没用对计算路径”的问题。

但只把 PP 做快还不够。处理完输入，马上就要开始生成，如果这时再慢吞吞恢复专家缓存，省下来的时间又会被切换过程吃回去。

因此，PP 接近结束时就开始预取后面生成要用的专家，优先照顾价值更高的层，同时给仍在进行的 PP 留出工作空间。

恢复过程也调整了顺序：先集中准备好目标空间，再连续提交拷贝，减少分配和传输交错造成的等待。

到 PP 真正结束，先释放那块专用暂存区，再根据剩余显存决定能恢复多少解码专家。等相关拷贝完成、专家表可用，再继续 TG。

“用完就还”很关键。暂存区如果一直留在缓存池里，看起来 PP 已经结束，它却还占着位置，后面的 TG 就少了一块能放热专家的显存。

动态 KV 则负责另一层平衡：上下文按需增长，专家缓存根据可用空间进退。再叠加这次 PP/TG 的阶段切换，显存就能随着当前任务重新分配。

不过，小消息不能照搬大消息的流程。

只追加几个 token，也把一大批专家卸下来再装回去，搬家的成本可能比计算还高。因此短输入继续利用已经热起来的单 token 混算路径；较长输入才切到批量 PP。

门槛还得看实际批次。原始请求可能被检查点拆小，调试时就遇到过：请求长度看着够了，拆出来的批次却没达到 GPU 门槛，又掉回慢路径。这个边界也一起处理了。

说完原理，来看数据。

同一台机器、同一个模型，先建立约 32k 的缓存，再追加 8192 个输入 token，生成 128 个 token。升级前后各跑两轮，模型精度、路由、批大小等主要条件保持一致。

这组追加输入的 PP：

152.2 tokens/s → 1176.2 tokens/s，约 7.73 倍。

包含处理输入和生成回答的整次请求：

56.81 秒 → 9.88 秒，耗时减少约 82.6%。

大 PP 后的 TG：

42.88 tokens/s → 43.68 tokens/s。

另一个单 token 追加场景，TG 是：

45.96 tokens/s → 45.07 tokens/s。

所以这次结果应该描述为：大幅缩短了处理输入的时间，主测试里的生成速度基本守住了。7.7 倍指的是这组 PP，不是整体生成速度涨了 7.7 倍。

此前还单独跑过 240000-token 输入。新版本完成了处理，PP 约 625.74 tokens/s，随后 TG 约 33.25 tokens/s。

边界与长上下文联合检查里，最低采样空闲显存约 428.83MiB，采样间隔是 0.2 秒。这个结果不能证明不存在更短的峰值，也不能说任何时刻都精确维持在 400—600MiB。有些形状仍会留下更高余量。

取舍也得讲。

加载后的第一个极短请求，初始化开销前移，首 token 等待反而变长了一些。后续迁移到 Qwen 时，也出现了部分短请求和小图没有变快的情况。因此，这还不是适用于所有负载的“完美平衡”。

而且主对照用的是固定的中文和代码重复片段，方便保证输入一致。真实聊天、工具调用和不同内容分布，还要继续观察，不能拿一组回放数据包打天下。

本轮没有降低模型或 KV 精度，没有减少路由选中的专家，也没有为了这个成绩加新的草稿模型。新做的 PP 暂存目前按计算流顺序复用，还不能说已经实现了双缓冲、把权重搬运和 GPU 计算全面重叠。

我更看重的进步是：终于开始按“现在是在读输入，还是在生成回答”来分配资源。

该让 GPU 批量处理时，把路打通；该靠热专家连续生成时，把空间还回去。连中间的搬运和切换时间，都要算进最终体验。
